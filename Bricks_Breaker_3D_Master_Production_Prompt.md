# BRICKS BREAKER 3D
## Master Production Prompt — Complete Game Vision, Mechanics, UX, Art Direction, Engineering, Monetization & ASO

> **Purpose:** This document is a master instruction prompt for an AI game-development team, designer, programmer, technical artist, UI/UX designer, sound designer, QA engineer, and product/ASO team. It converts the original Zen Bricks concept into a production-oriented specification for a new game titled **Bricks Breaker 3D**.
>
> **Important naming decision:** The working and product name throughout this document is **Bricks Breaker 3D**. The phrase “Zen Bricks” is intentionally removed from player-facing naming. The experience should communicate a premium, modern 3D brick-breaking game with dense ball swarms, satisfying destruction, spatial deflection, lasers, bombs, and progression.
>
> **Source basis:** This specification preserves the major concepts from the supplied Zen Bricks master document: mega-density grids, 300–600+ blocks, 100–500+ balls, 45° triangular wedge deflectors, two types of + ball multipliers, laser and bomb entities, architectural level archetypes, neon/OLED visual treatment, pentatonic collision audio, portrait/landscape HUD concepts, rewarded monetization, Flutter/CustomPainter architecture, and ASO positioning. The original document states these as design targets; performance numbers in this expanded document are treated as targets to validate during implementation rather than guaranteed results.

# 00. MASTER DIRECTIVE

Build **Bricks Breaker 3D** as a polished, highly replayable mobile brick-breaker game whose core fantasy is:

**“Aim one shot, create a ball swarm, infiltrate impossible-looking structures, trigger chain reactions, and watch hundreds of balls destroy a 3D field of bricks in a single satisfying run.”**

The game must never feel like a generic Breakout clone. Its differentiation must be visible within the first gameplay screenshot and understandable within the first five seconds:

1. The playfield is unusually dense.
2. Bricks and structural pieces have depth and 3D presentation.
3. Balls can multiply dramatically.
4. Geometry intentionally redirects balls into traps and chambers.
5. Lasers, bombs, cross-beams and special structures create chain reactions.
6. Destruction is satisfying, readable and visually rich without becoming confusing.
7. The player’s primary skill is trajectory planning, not rapid tapping.
8. The game should support short sessions but contain enough progression to encourage daily return.
9. The product should be viable for organic app-store acquisition through clear search intent and strong creative differentiation.

Do not dilute the game into a feature checklist. Every system must reinforce the central loop:

**Observe → Aim → Fire → Multiply → Infiltrate → Chain-react → Clear → Collect → Improve → Repeat.**

The project should be architected so that the core simulation, presentation, progression, content generation and monetization are separable. This allows the team to tune game balance without rewriting the renderer or UI.

# 02. PRIMARY GAMEPLAY LOOP

## 2.1 Turn Structure

Each turn follows this sequence:

### Phase A — Observe

The player sees:

- the current brick architecture
- current brick values/health
- special blocks
- + multipliers
- bombs
- laser blocks
- deflector wedges
- danger line
- current ball count
- available boosters

### Phase B — Aim

The player drags or touches to set an initial trajectory.

The trajectory system must show a clean predicted path for the initial shot. It may show one or more predicted reflections depending on a user-facing difficulty setting.

The aim system must prevent accidental vertical lock-in. Maintain a controllable minimum horizontal component unless a level explicitly requires a vertical shot.

### Phase C — Fire

The launcher releases the entire current ball count according to the selected spread logic.

Important:

- Never fire 500 balls in literally the same mathematical line.
- Introduce tiny deterministic offsets or controlled spread so the swarm visually reads as a dense stream.
- Preserve fairness and predictable trajectory behavior.

### Phase D — Simulation

Balls collide with:

- screen walls
- bricks
- triangular deflectors
- special entities
- optional temporary fields

Events should be queued or processed through a robust simulation architecture to avoid order-dependent bugs.

### Phase E — Multiplication

When balls hit a split/cloner object, the object can create additional active balls.

Permanent + items increase future ammunition.

### Phase F — Chain Reaction

Bombs and lasers should trigger deterministic, visually readable reactions.

A chain reaction should feel like the player discovered a structure that was waiting to collapse.

### Phase G — Collection / End of Turn

Resolve:

- collected permanent balls
- score
- combo
- coins/gems
- completed objectives
- booster effects
- level completion/failure

### Phase H — Board Advance

If the design includes downward progression after every turn, lower the brick structure by exactly one logical row or another level-authored increment.

Never move the board unexpectedly during an active ball simulation.

### Phase I — Next Aim State

Reset the launcher to the correct horizontal starting position and present the next target state.

# 03. THE CORE DIFFERENTIATOR: MEGA-DENSITY + BALL SWARMS

The supplied source defines a mega-density philosophy in which a screen may contain approximately 20–30 columns and 35–50 rows, with 300–600+ visible blocks and potentially 100–500+ simultaneous balls.

For Bricks Breaker 3D, treat those figures as **high-end design targets**, not hard promises that every device must sustain without profiling.

## 3.1 Density Tiers

Create performance/content tiers:

### Tier 1 — Intro

- 8–14 columns
- 10–18 rows
- 10–50 active balls
- limited special blocks
- simple geometry

### Tier 2 — Core

- 12–18 columns
- 18–28 rows
- 30–150 active balls
- mixed structures

### Tier 3 — Mega

- 15–25 columns
- 25–40 rows
- 100–300 active balls
- dense special interactions

### Tier 4 — Extreme

- up to 20–30 logical columns
- up to 35–50 logical rows
- 300–500+ active balls where profiling validates feasibility
- multiple simultaneous chain reactions

The player should encounter Tier 4 moments as special experiences rather than having the entire game permanently run at maximum complexity.

## 3.2 Why Density Matters

Density is not present simply to put more objects on screen.

Density creates:

- more potential trajectories
- more opportunities for ball multiplication
- higher chain-reaction probability
- visually impressive destruction
- more meaningful geometry
- stronger trailer/screenshot moments

Every dense board must still have a readable strategic structure.

# 04. 3D GAMEPLAY PRESENTATION

## 4.1 Definition of “3D”

Bricks Breaker 3D should visually communicate three dimensions even if the simulation remains primarily 2D or 2.5D for performance and control simplicity.

Recommended approach:

**2D deterministic gameplay simulation + 3D-rendered or 3D-styled presentation.**

This preserves the predictable trajectory gameplay while allowing:

- beveled bricks
- depth shading
- camera parallax
- perspective compression
- particle depth
- layered shadows
- dynamic highlights
- 3D-looking explosions

## 4.2 Camera

Default camera:

- slightly elevated
- fixed gameplay framing
- no unnecessary rotation during normal play

Use subtle camera movement only for special events:

- nuke
- mega chain
- level boss clear
- large combo

Do not make camera shake so strong that the player loses track of the projectile path.

## 4.3 Brick Depth

Every standard brick should have:

- front face
- thin extrusion/depth
- edge highlight
- soft shadow or ambient occlusion approximation
- health indicator

Special bricks should have stronger visual identity but stay within the same rendering language.

## 4.4 Depth Hierarchy

Use three visual depth bands:

1. **Background:** subtle, low-contrast depth and atmospheric layers.
2. **Gameplay plane:** bricks, wedges, lasers, bombs and balls.
3. **Foreground feedback:** particles, score bursts and temporary effects.

Never let foreground effects permanently obscure the gameplay plane.

# 05. SPATIAL GRID AND PLAYFIELD

## 5.1 Logical Grid

The simulation uses a logical grid independent of device resolution.

Example:

- 20 columns
- 40 rows
- one logical cell contains one primary block or a defined multi-cell structure

Render the logical grid into a viewport rectangle.

## 5.2 Cell Coordinates

Each block must have:

- integer grid coordinate
- stable unique ID
- type
- health
- maximum health
- tags
- special state
- visual state
- collision geometry

Recommended data concept:

```text
Brick
 ├─ id
 ├─ cellX
 ├─ cellY
 ├─ width
 ├─ height
 ├─ type
 ├─ health
 ├─ maxHealth
 ├─ destroyed
 ├─ rotation
 ├─ state
 └─ tags[]
```

## 5.3 Spatial Hash / Broad Phase

The supplied source proposes a spatial hash grid for reducing collision work when hundreds of balls and hundreds of bricks are active.

Implement the broad phase so the engine does not test every active ball against every block on every simulation substep.

The system should:

1. Map each brick into one or more spatial buckets.
2. Determine the ball’s current bucket.
3. Query nearby buckets.
4. Narrow-phase test only candidate colliders.
5. Resolve collisions deterministically.

Do not hard-code an assumption that a particular percentage reduction will always occur. Measure it on target hardware.

# 06. BALL SYSTEM

## 6.1 Ball Data

Each ball should have:

- unique ID
- position
- velocity
- radius
- active state
- spawn generation
- source ball ID
- optional trail state
- optional temporary modifiers
- collision cooldown data

Optional advanced fields:

- damage multiplier
- speed multiplier
- penetration count
- elemental state
- visual skin

## 6.2 Ball Speed

Gameplay must prioritize readable trajectories over physically realistic speed.

Keep the velocity range controlled so that:

- players can follow the shot
- collisions remain stable
- low-end hardware has enough simulation time
- balls do not tunnel through thin blocks

Use continuous collision techniques, substeps or swept collision checks when necessary.

## 6.3 Ball Swarm

A swarm should visually read as:

**one powerful stream composed of many individually simulated balls.**

Use:

- tiny spacing variation
- subtle speed variation within fairness limits
- short glowing trails
- occasional particle sparks

Do not randomize physics after the shot begins in ways that make the outcome unpredictable.

## 6.4 Minimum Ball Count

A player should never lose the feeling of being able to build a swarm.

The early progression should gradually demonstrate:

10 → 15 → 25 → 40 → 75 → 100+

and later:

150 → 250 → 300 → 500+

where content and device performance support it.

# 07. TRAJECTORY AIMING SYSTEM

## 7.1 Input

Primary input:

**drag from the launcher toward the intended direction.**

Release fires.

Alternative implementation:

- touch-and-drag anywhere in an aim zone
- launcher follows horizontal finger movement
- shot direction uses a constrained vector

## 7.2 Aim Assist

The aim system should offer configurable assistance:

### Beginner

Predict up to 3 reflections.

### Standard

Predict the first reflection and selected special interactions.

### Expert

Minimal prediction.

### Accessibility

Longer trajectory visualization and stronger collision indication.

## 7.3 Trajectory Line

Use a fine luminous line.

The line must:

- disappear immediately after firing
- not cover numbers inside blocks
- stop or change style when entering a special zone
- remain visually subtle compared with the actual balls

## 7.4 Anti-Frustration Rules

Do not allow:

- perfectly horizontal accidental shots as the default outcome
- impossible collision angles caused by rounding errors
- balls permanently trapped with no return path unless intentionally designed
- immediate loss because the launcher was released one pixel differently

# 08. BLOCK TAXONOMY

Bricks Breaker 3D inherits the source document’s broad entity taxonomy while expanding it into a production-ready system.

## 8.1 Standard Rectangle

Properties:

- health
- front-face material
- damage crack state
- destruction effect

Behavior:

- loses one or more health points per hit
- destroyed at zero health

## 8.2 45° Wedge Family

Required types:

- Triangle Top Left
- Triangle Top Right
- Triangle Bottom Left
- Triangle Bottom Right

Purpose:

- redirect balls
- create funnels
- create chambers
- increase tactical complexity
- support multi-bounce setups

## 8.3 Permanent Ball Adder

Visual:

- luminous + symbol
- distinct orbit or ring
- strong pickup feedback

Behavior:

When a ball touches the item:

- collect item
- increment permanent ball ammunition by one
- remove item
- show +1 feedback

Important:

The additional ball is added to future shots unless the current level explicitly defines a different rule.

## 8.4 In-Air Ball Splitter

Visual:

- bright cyan/green + symbol
- floating or embedded orb

Behavior:

When touched during flight:

- consume splitter
- create one additional ball
- preserve meaningful momentum
- offset the clone trajectory by a controlled angle

A 90° offset is a valid baseline from the source, but tune it based on level readability and collision stability.

## 8.5 Horizontal Laser

On destruction:

- fire across the row
- damage or destroy designated targets
- display beam for a very short readable duration
- emit audio cue

## 8.6 Vertical Laser

Same concept along the column.

## 8.7 Cross Beam

Emits horizontal and vertical effects simultaneously.

## 8.8 Diagonal Laser

Optional advanced entity:

- X-shaped beam
- intended for later levels
- should communicate its activation clearly

## 8.9 Cluster Bomb

A 3×3 logical area is the baseline.

The bomb should:

- display a warning/armed state before detonation where appropriate
- destroy or damage nearby targets
- create radial shockwave
- spawn fragments
- optionally trigger neighboring special blocks

## 8.10 Chain Dynamite

A chain-capable explosive should be treated as a content-system feature rather than a physics explosion that spreads infinitely.

Use a bounded propagation algorithm.

## 8.11 Super Nuke

Rare high-value special.

Source behavior:

Destroy every block with health ≤ 10.

Alternative content variants may:

- clear all low-health blocks
- wipe a selected percentage
- initiate a board-wide damage pulse

The exact rule must be visible in the tutorial or power-up description.

## 8.12 Lightning

Lightning should be a high-impact targeted effect.

Possible behavior:

- chain through selected blocks
- prioritize high-health targets
- avoid infinite recursion

## 8.13 Freeze / Ice

Optional control mechanic:

- temporarily stops selected block movement or special timers
- changes visual material to icy glass
- reduces incoming danger for one turn

# 09. 45-DEGREE DEFLECTOR PHYSICS

The source defines standard vector reflection using:

**V' = V - 2(V · N)N**

For a 45° surface this creates highly readable direction changes.

Implement the general normal-vector equation rather than hard-coding only one special-case formula where practical.

## 9.1 Collision Process

For a wedge collision:

1. broad-phase candidate
2. determine closest point / triangle edge
3. identify active collision edge
4. calculate surface normal
5. reflect velocity
6. apply controlled positional separation
7. register damage/event
8. place the ball outside the surface enough to prevent repeated overlap

## 9.2 Numerical Stability

Avoid:

- velocity zeroing
- infinite repeated collision loops
- same-frame double hit on a destroyed block
- ball embedding in corners
- energy growth caused by rounding errors

## 9.3 Strategic Geometry

Wedges should not be random decoration.

Every wedge placement should serve at least one purpose:

- redirect into a chamber
- create a difficult angle
- protect a special block
- create a risk/reward pocket
- generate multiple rebound paths
- create a funnel

# 11. FUNNEL INFILTRATION DESIGN

This mechanic is a signature feature and should appear in marketing footage.

A funnel infiltration level is built around:

1. a dense outer layer
2. one or more intentional gaps
3. a protected chamber
4. valuable special blocks
5. a route allowing many balls to enter
6. a visual moment where the swarm appears to “pour” into the structure

The player should be able to understand the goal before firing.

A successful funnel moment should produce:

- camera micro-push
- stronger particle density
- ball trails
- controlled slow-motion or time compression for less than one second
- audio escalation
- visible chain events

Avoid long cinematic interruptions. The game is still active and should remain interactive.

# 12. LEVEL DIFFICULTY MODEL

## 12.1 Difficulty Inputs

Do not scale difficulty only through brick health.

Use a multidimensional model:

- brick health
- density
- corridor width
- special-block placement
- number of safe angles
- danger-line movement
- board topology
- multiplier availability
- expected ball count
- turn budget

## 12.2 Difficulty Curve

Early game:

- teach one mechanic at a time

Mid game:

- combine two systems

Advanced:

- combine three or four systems

Master:

- intentionally stack geometry, multipliers and chain effects

## 12.3 Fail State

Failure should be readable.

The player loses when the active board reaches the defined danger threshold.

Before failure:

- show danger line
- use subtle warning animation
- avoid sudden full-screen red overlays

After failure:

Present:

- level result
- score
- balls acquired
- best score comparison
- optional rewarded continue
- retry
- exit/map

# 13. SCORE SYSTEM

Suggested factors:

```text
Base Brick Damage
+ Block Destruction
+ Combo Hits
+ Special Trigger
+ Chain Reaction
+ Multi-Ball Bonus
+ Chamber Infiltration Bonus
+ Near-Danger Survival Bonus
= Turn Score
```

Avoid creating a score formula so complicated that players cannot understand what caused a high score.

## 13.1 Combo

A combo increases when the player causes continuous damage without an excessive gap.

Example conceptual thresholds:

- 10 consecutive hits: Combo x2
- 25 hits: Combo x3
- 50 hits: Combo x4
- 100 hits: Mega Combo

Use adaptive thresholds so early content does not become trivial.

## 13.2 Chain Score

Award additional score for:

- laser → laser
- bomb → laser
- splitter → bomb
- bomb → bomb

Chain depth must be capped for score stability and analytics clarity.

Then use controlled octave movement as hit density increases.

Do not trigger a full sample on every collision when hundreds of collisions happen per second.

Use:

- event batching
- voice limiting
- pitch variation
- velocity mapping
- priority rules

## 24.2 Audio Layers

### Layer 1

Soft brick hit.

### Layer 2

Higher-pitched multiplier hit.

### Layer 3

Laser activation.

### Layer 4

Bomb impact.

### Layer 5

Mega-chain sub-bass.

## 24.3 ASMR Goal

The sound should feel tactile and satisfying rather than aggressive.

Avoid harsh repeated clicks.

# 25. PERFORMANCE ARCHITECTURE

The original document targets high-density Flutter rendering.

Use a performance-first design.

## 25.1 Main Principles

- separate simulation and rendering
- avoid unnecessary widget rebuilds
- use custom painting or a game engine layer for dense scenes
- use object pooling
- batch particles
- use broad-phase collision acceleration
- avoid allocations inside hot loops
- profile on real devices

## 25.2 Frame Budget

A target of 120 FPS means approximately:

**8.33 ms per frame.**

A target of 60 FPS means approximately:

**16.67 ms per frame.**

The game should dynamically scale nonessential effects when needed.

## 25.3 Quality Tiers

### Low

- reduced particles
- no expensive distortion
- shorter trails
- lower simultaneous effect count

### Medium

- normal trails
- moderate particles
- bloom approximation

### High

- full effects
- more debris
- advanced lighting

### Ultra

- maximum supported effects

Never sacrifice simulation determinism to increase visual quality.

# 26. SIMULATION LOOP

Recommended conceptual loop:

```text
Input
  ↓
Aim State
  ↓
Fire Command
  ↓
Simulation Step
  ↓
Broad Phase
  ↓
Narrow Phase
  ↓
Collision Resolution
  ↓
Event Queue
  ↓
Special Effects / Chain Logic
  ↓
State Commit
  ↓
Render
```

Do not mutate the same collection while iterating through it in ways that cause unstable ordering.

Example:

If a splitter creates 50 new balls while iterating over balls, append spawn requests to a queue and commit them after the active-ball iteration.

# 28. COLLISION RESOLUTION PRIORITY

A single collision frame can generate multiple possible interactions.

Define a deterministic order.

Recommended:

1. movement update
2. wall collision
3. solid geometry collision
4. special collectible collision
5. destruction state update
6. queued special effects
7. chain propagation
8. score events
9. visual/audio events

Do not let event order depend on list iteration order if that could change gameplay outcome.

# 29. BALL SPLITTER LOGIC

When a ball touches an active splitter:

1. Validate splitter is not already triggered.
2. Mark it triggered.
3. Destroy/remove splitter.
4. Register original-ball hit.
5. Create clone spawn request.
6. Calculate controlled new direction.
7. Preserve magnitude unless the design calls for a modifier.
8. Spawn after collision iteration.
9. Play feedback.

Example conceptual split:

```text
original velocity = V
clone velocity = rotate(V, +90°)

optional second clone:
rotate(V, -90°)
```

Do not allow a splitter to recursively duplicate itself unless explicitly authored.
